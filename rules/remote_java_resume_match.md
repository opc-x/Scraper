# 规则：Java / Agent 职位 · 简历匹配打分

适用范围：**全部职位渠道**（`boss`、`telegram`、`discord`、`x`、`jobboards`=RemoteOK+WeWorkRemotely、`youtube`、`v2ex`），统一作用于 `scraped_jobs` 表，不是某一个渠道专属。

## 判定标准（AND，全要，三条都满足才算命中）

1. **方向匹配**：技术栈明确包含 Java / JVM 系，或者职责明确是 AI/LLM Agent 编程开发；泛 Python、前端、产品、运营和只写“AI”的岗位不算。
2. **地点可行**：明确远程，或者现场 / 混合办公地点在杭州；其他城市纯现场岗一律不算。
3. **外语环境**：明确写有英语/日语办公、国际化/海外团队或日常外语沟通；只因 JD 是英文不能自动推断为外语工作环境。

三条有一条不满足，不算命中，不打分，不进候选池——不要为了凑数放宽标准。

## 匹配度打分（0-100，基于简历 `docs/resumes/consolidated_2026.md`）

简历定位：Java 后端负责人 / 技术专家，分布式 & 大数据（Kafka、Elasticsearch、Hadoop、Spark、Hive、Flink、Storm），多年团队管理（3-20 人不等），多次「从零到一」搭建数据平台/中台经验。

打分维度（每维等权，加权平均取整）：
- **技术栈重合度**：职位要的技术栈跟简历里的 Java/Kafka/ES/Spark/Flink 等重合越多分越高
- **级别匹配度**：职位要的资历（senior/staff/负责人/架构师）跟简历「技术专家/负责人」这条线对不对得上
- **管理经验相关性**：职位是否要带团队/跨部门协调——简历这块经验丰富，命中就加分
- **地域可行性**：中国大陆能否合法远程投递这个职位（时区、工作许可、签证要求），基本无望的直接压低分数而不是无视

分档：
- **85-100**：技术栈+级别+管理经验都对得上，强烈推荐
- **65-84**：技术栈对得上，级别或管理经验有一项不完全匹配
- **40-64**：技术栈部分重合，级别偏低或偏高
- **0-39**：勉强算远程Java但整体不匹配，不建议投

## 打分怎么跑

不在生产 API 请求里现算（`CLAUDE.md`「本地 AI 挖掘环境」的规矩：生产不发起本机 Claude CLI 之外的批量 LLM 调用，这条走本机 `claude` CLI 订阅，本身就只能在本机跑）。跑法见 `scripts/score_jobs.py`：

```bash
python -m scripts.score_jobs                # 默认扫近 90 天、还没打过分的 scraped_jobs
python -m scripts.score_jobs --days 30       # 只看最近 30 天
python -m scripts.score_jobs --refresh       # 已打过分的也重新算一遍（简历改了之后用这个）
python -m scripts.score_jobs --channel v2ex  # 只跑单个渠道
```

打分结果写入 `job_profiles` 表（跟 `/api/jobs/{id}/profile` 手动生成画像是同一张表，脚本是批量版，`app/api/routes/jobs.py` 里那条 prompt 已经改成直接读简历原文，不再是写死的过期背景描述）。

## 关于"数量"

这条规则的产出量级取决于：① 各渠道当期真实存在多少满足"远程+Java+简历匹配"的职位 ② 打分严格程度。**不设固定条数下限**——为了凑数放宽判定标准，或者把打分不够高的也硬塞进候选池，都是反规则本身的行为，宁可条数少，不要注水。想要更多，去增加渠道覆盖面或者放宽抓取关键词，而不是放宽这条打分标准。
